# CTO Review — Technical Credibility, Architecture, and Hiring Risk

You are reviewing Sebastian Marin's portfolio as if you were the CTO of Geolabs Cloud.

Your job is to determine whether the portfolio provides credible technical evidence that Sebastian can contribute to a PHP/MySQL/PostgreSQL/Linux/API/AI/geospatial web platform.

Be skeptical. Be fair. Do not reward buzzwords.

## Inputs

Use the following in this order:

1. Live portfolio URL.
2. Project demos linked from the portfolio.
3. GitHub repositories linked from the portfolio.
4. CV/resume only after portfolio review.
5. Source code, if available.

## Review Sequence

Do not start by reading code.

First act like a technical hiring manager reviewing the live portfolio.

Then inspect GitHub/code only for projects that seem important or suspicious.

## Role Context

The official Geolabs role values:

- PHP intermedio-avanzado with real production experience;
- interactive responsive web interfaces;
- MySQL/PostgreSQL, PostGIS desirable;
- cURL and REST API integrations;
- Linux CLI, cron jobs and process debugging;
- habitual use of AI tools and agents;
- geospatial, maps, photogrammetry or GIS;
- Git and clean documented code;
- MCP experience desirable.

Do not penalize the candidate for lacking every optional skill, but identify gaps honestly.

## Primary Goal

Answer:

Does this portfolio increase or decrease my confidence compared to the CV?

## Browser Review

Open the live site and inspect:

- homepage clarity;
- project pages;
- project demos;
- GitHub links;
- responsiveness;
- performance;
- console errors;
- broken links;
- fake or non-functional projects;
- claims that are not backed by demos/code.

Use browser DevTools if available.

Check at least:

- desktop width;
- mobile width around 390px;
- one tablet-ish width if practical.

## Code Review Scope

If source code is available, inspect selectively:

- project structure;
- TypeScript usage;
- component organization;
- data model;
- API routes;
- error handling;
- SQL/PHP code if present;
- README quality;
- environment handling;
- security practices;
- whether credentials are exposed;
- whether demos are hardcoded;
- whether project claims match implementation;
- whether Git history looks realistic.

Do not waste time reviewing every line.

## Questions to Answer

### 1. Technical Signal

- What technical signal is strongest?
- What technical signal is weakest?
- Which project best supports the Geolabs role?
- Which project feels irrelevant or weak?

### 2. Red Flags

Flag:

- broken demos;
- non-working side projects;
- fake buttons;
- hardcoded data presented as dynamic;
- exaggerated AI claims;
- exaggerated PHP/PostGIS/MCP claims;
- inaccessible GitHub repos without explanation;
- missing README files;
- poor mobile behavior;
- console errors;
- obvious AI-generated copy.

### 3. Geolabs Role Fit

Assess fit for each official requirement:

| Requirement | Evidence in portfolio | Strength |
|---|---|---|
| PHP |  | strong / medium / weak / missing |
| Interactive responsive UI |  | strong / medium / weak / missing |
| MySQL/PostgreSQL |  | strong / medium / weak / missing |

| MCP |  | strong / medium / weak / missing |

### 4. Portfolio vs CV

After reviewing the portfolio, compare it with the CV.

- Does the portfolio support the CV claims?
- Does the CV explain strengths that the portfolio fails to show?
- Is there any mismatch or credibility issue?
- Should the portfolio mention fewer things but show them better?

### 5. Technical Fixes

Give practical recommendations:

- what to fix before sending;
- what to hide until working;
- what to move to "Labs";
- what to document better;
- what to remove entirely.
